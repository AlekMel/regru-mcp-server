## 1. Архитектура и фундаментальные принципы взаимодействия

### 1.1. Транспортный протокол и методы (Strict HTTPS POST)
Все вызовы к REG.API 2.0 осуществляются исключительно по протоколу HTTPS ([официальная документация Рег.API 2.0](https://www.reg.ru/reseller/api2doc)).
- **Метод запроса:** Строго **POST**. Запросы методом GET полностью прекращены и возвращают ошибку `ONLY_POST_ALLOWED`.
- **Передача параметров в Query String строго запрещена:** попытка передать параметры в URL (например, `?username=foo`) отклоняется с ошибкой `QUERY_PARAMS_DISALLOWED`.
- **Синхронность и атомарность:** Каждый API-вызов является синхронным — результат операции возвращается сразу в теле ответа HTTP 200, промежуточных polling-состояний нет.

### 1.2. URL-структура эндпоинтов
Каждая функция API имеет строго индивидуальный URI-эндпоинт:
```text
https://api.reg.ru/api/regru2/<имя_категории>/<имя_функции>
```
Примеры:
- `https://api.reg.ru/api/regru2/zone/get_resource_records` — чтение DNS-записей зоны;
- `https://api.reg.ru/api/regru2/domain/check` — проверка доступности домена;
- `https://api.reg.ru/api/regru2/service/get_list` — получение списка всех активных услуг аккаунта.

### 1.3. Форматы входных данных (JSON inside form-data)
Для надежной передачи сложных иерархических структур данных (массивы доменов, вложенные контакты, списки DNS-серверов) REG.API 2.0 использует передачу сериализованного JSON через стандартный POST-параметр `input_data` с типом формы `application/x-www-form-urlencoded`:
```http
POST /api/regru2/zone/add_alias HTTP/1.1
Host: api.reg.ru
Content-Type: application/x-www-form-urlencoded; charset=utf-8

username=my_login&password=my_api_password&input_format=json&output_format=json&input_data=%7B%22domains%22%3A%5B%7B%22dname%22%3A%22example.com%22%7D%5D%2C%22subdomain%22%3A%22www%22%2C%22ipaddr%22%3A%221.2.3.4%22%7D
```

> **Критическое правило безопасности:** Параметры аутентификации (`username`, `password` или `sig`) **НЕ ДОЛЖНЫ** передаваться внутри JSON-объекта `input_data`. Они передаются как отдельные параметры первого уровня POST-формы.

### 1.4. Форматы выходных данных и унифицированный контракт ответа
Стандартный формат ответов — **JSON** (`output_format=json`).

#### Положительный ответ (`result: "success"`)
```json
{
  "result": "success",
  "answer": {
    "service_id": "123456",
    "domains": [
      {
        "dname": "example.com",
        "result": "success"
      }
    ]
  },
  "charset": "utf-8",
  "messagestore": null
}
```

#### Ответ с ошибкой (`result: "error"`)
```json
{
  "result": "error",
  "error_code": "DOMAIN_ALREADY_EXISTS",
  "error_text": "Domain example.com already registered",
  "error_params": {
    "domain_name": "example.com"
  },
  "charset": "utf-8"
}
```

### 1.5. Кодировки и локализация
- **Кодировка по умолчанию:** `utf-8`. Поддерживаются параметры `io_encoding` и `output_encoding` (cp1251, koi8-r, koi8-u, cp866). Для MCP-сервера рекомендуется строго фиксировать `utf-8`.
- **IDN и кириллические домены:** Рекомендуется передавать русские имена доменов (зоны `.рф`, `.рус` и IDN) в представлении Punycode (например, `xn--p1ai`), либо в UTF-8. При некорректном формате возвращается ошибка `INVALID_DOMAIN_NAME_PUNYCODE`.
- **Локализация сообщений об ошибках:** По умолчанию сообщения об ошибках дублируются на русском и английском языках в структурированном виде.

### 1.6. Лимиты обращений (Rate Limits) и правила параллелизма
1. **Жесткий лимит частоты:** **1200 запросов в час** на одного клиента и **1200 запросов в час** на один IP-адрес. Оба лимита действуют одновременно. При превышении возвращается `ACCOUNT_EXCEEDED_ALLOWED_CONNECTION_RATE` или `IP_EXCEEDED_ALLOWED_CONNECTION_RATE` с блокировкой на скользящий час.
2. **Параллелизм:** Параллельные вызовы разрешены **только для нефинансовых операций** (просмотр DNS, проверка статусов, чтение списков). Все операции, изменяющие баланс или связанные с биллингом (`domain/create`, `service/renew`, `bill/*`), блокируют параллельное выполнение — при конкурентном вызове возвращается ошибка `BILLING_LOCK`.
3. **Рекомендация Рег.ру:** Запросы на регистрацию и изменение данных в клиенте/MCP-сервере **должны выполняться через асинхронную очередь с одним потоком** для финансовых вызовов.

## 2. Система аутентификации и безопасность

### 2.1. Белый список IP-адресов (IP Whitelisting)
> **Критический нюанс:** Если в панели управления Рег.ру в разделе «Настройки API» не добавлен ни один IP-адрес сервера, вызовы API **полностью заблокированы** с ошибкой `ACCESS_DENIED_FROM_IP`. Сервер, на котором разворачивается MCP-сервер, должен иметь постоянный внешний статический IP-адрес, прописанный в личном кабинете Рег.ру.

### 2.2. Аутентификация по логину и паролю API (Username + API Password)
Наиболее удобный метод для MCP-сервера:
- `username` — логин учетной записи в Рег.ру (или e-mail, если он уникален).
- `password` — специальный пароль для API, задаваемый в настройках безопасности личного кабинета (настоятельно не рекомендуется использовать мастер-пароль от веб-кабинета).

### 2.3. Аутентификация по криптографической подписи (RSA SHA512 Signature)
Повышенный уровень безопасности для финансовых и партнерских интеграций:
- `username` — логин учетной записи.
- `sig` — Base64-строка RSA-подписи SHA512-хеша параметров.
- **Алгоритм формирования подписи:**
  1. Берутся все скалярные строковые значения передаваемых параметров (включая `username`).
  2. Пустые строки, нулевые значения `0`, `null`/`undefined` и группирующие массивы отбрасываются.
  3. Оставшиеся значения сортируются в лексикографическом порядке (ASCII / UTF-8 байты).
  4. Значения конкатенируются через точку с запятой `;` (например: `1;1;2;3;plain;qqq.ru;test`).
  5. Строка подписывается приватным RSA-ключом (SHA512) и кодируется в Base64.
- Публичный сертификат предварительно загружается в настройках API Рег.ру.

### 2.4. Аутентификация с клиентским SSL-сертификатом (mTLS)
При включенной опции в личном кабинете каждый HTTP-запрос должен сопровождаться клиентским SSL-сертификатом (заголовки TLS-сессии, директивы `--cert` и `--key` в cURL / HTTPS Agent).

### 2.5. Тестовый режим песочницы (Sandbox: `test/test`) vs Боевой режим
- Для безопасной отладки MCP-сервера предусмотрен встроенный режим песочницы: параметры `username=test` и `password=test`.
- В режиме `test`: сервер Рег.ру производит полную синтаксическую валидацию входных параметров, проверяет схемы данных, но реальные заказы не создаются, DNS-записи не модифицируются, а средства с баланса не списываются.
- **Диагностические методы `nop`:** Для каждого модуля предусмотрен вызов `<модуль>/nop` (`domain/nop`, `zone/nop`, `service/nop`, `bill/nop`, `user/nop`, `folder/nop`, `dnssec/nop`, `hosting/nop`, `shop/nop`), позволяющий тестировать доступ и авторизацию с минимальным временем отклика.

## 3. Стандартизованные модели параметров и схемы данных

### 3.1. Унифицированная идентификация услуг и доменов
Любая операция над существующим объектом (доменом, хостингом, сертификатом) требует его идентификации одним из 4 способов:
1. **По `service_id` (Числовой ID услуги в Рег.ру) — САМЫЙ БЫСТРЫЙ И РЕКОМЕНДУЕМЫЙ СПОСОБ.** Подходит как для доменов, так и для любых услуг.
2. **По `domain_name` / `dname`:** Применимо для доменов (например, `domain_name=example.com`).
3. **По связке `domain_name` + `servtype`:** Для прикладных услуг, привязанных к домену (например, `domain_name=example.com&servtype=srv_hosting_ispmgr`).
4. **Пользовательский идентификатор `user_servid`:** 32-символьная строка (hex/alphanumeric), если она была задана клиентом при создании услуги.

### 3.2. Массовая пакетная обработка (Batch Processing до 1000 объектов)
Многие методы (включая `zone/get_resource_records`, `zone/add_alias`, `domain/get_nss`, `service/get_info`) поддерживают одновременную обработку массива объектов (до 1000 штук в одном вызове):
```json
{
  "domains": [
    {"dname": "alpha.ru"},
    {"dname": "beta.com"},
    {"service_id": "987654"}
  ]
}
```
Ответ в таком случае содержит массив `domains` или `services`, где для каждого отдельного элемента указан локальный статус `result: "success"` или `result: "error"` с кодом ошибки.

### 3.3. Параметры биллинга и списания средств
- `pay_type`: Способ оплаты заказа счёта:
  - `prepay` — списание с лицевого баланса аккаунта Рег.ру (по умолчанию; только при этом типе операция выполняется автоматически);
  - `bank` / `pbank` — генерация банковской квитанции/счета;
  - `yacard` — банковская карта онлайн.
- `ok_if_no_money`: Булевый флаг (`0` или `1`):
  - `0` (по умолчанию) — если средств на балансе недостаточно, операция прерывается с ошибкой `NOT_ENOUGH_MONEY`, счет не создается;
  - `1` — разрешить выставить неоплаченный счет в системе Рег.ру даже при нулевом балансе (заказ встанет в статус ожидания оплаты).

### 3.4. Модели контактных данных и идентификация персон
При регистрации доменов (`domain/create`) или заказе услуг передается объект `contacts`:
- **Физическое лицо (Person):**
  - `p_addr_zip`, `p_addr_city`, `p_addr_street`, `p_addr_house`, `p_addr_flat` (Почтовый адрес);
  - `phone` (в международном формате: `+7 495 1234567`), `e_mail`;
  - `passport` (серия, номер, кем выдан, дата выдачи: `34 02 651241 выдан 48 о/м г.Москвы 26.12.1990`);
  - `birth_date` (ДД.ММ.ГГГГ), `code` (ИНН физического лица, если есть).
- **Юридическое лицо (Organization):**
  - `org` (наименование латиницей), `org_r` (полное наименование по ЕГРЮЛ на русском);
  - `code` (ИНН, 10 или 12 знаков), `kpp` (КПП, 9 знаков);
  - `address_r_zip`, `address_r_city`, `address_r_street`, `address_r_house` (Юридический адрес);
  - `phone`, `e_mail`.
- **Регулирование и верификация через ЕСИА Госуслуги (ФЗ № 569-ФЗ):**
  Для доменных зон `.ru`, `.su`, `.рф` операции делегирования и регистрации требуют подтвержденного статуса идентификации администратора через Госуслуги (ЕСИА). Метод `user/get_persons` возвращает статус `esia_status` по каждой персоне аккаунта.

### 3.5. Модели DNS-серверов (`nss`)
DNS-сервера передаются либо плоскими полями `ns0`...`ns3`, либо объектом `nss`:
```json
{
  "nss": {
    "ns0": "ns1.reg.ru",
    "ns1": "ns2.reg.ru",
    "ns2": "ns3.mycustomdomain.ru",
    "ns2ip": "195.208.1.1"
  }
}
```
Если NS-сервер находится на самом делегируемом домене (Glue Record), обязательно передается сопутствующий IP-адрес через `nsXip`.

## 4. Ошибки REG.API 2.0 (кратко)
Ответ с `result: "error"` содержит `error_code`, `error_text`, `error_params`.
Важные коды: `ACCESS_DENIED_FROM_IP`, `ONLY_POST_ALLOWED`, `QUERY_PARAMS_DISALLOWED`,
`ACCOUNT_EXCEEDED_ALLOWED_CONNECTION_RATE`, `IP_EXCEEDED_ALLOWED_CONNECTION_RATE`,
`BILLING_LOCK`, `NOT_ENOUGH_MONEY`, `DOMAIN_ALREADY_EXISTS`, `INVALID_DOMAIN_NAME_PUNYCODE`.
Полный классификатор — в официальной документации REG.API 2.0.

## 5. Методы API
Всего 116 методов в категориях: root, user/*, bill/*, service/*, domain/*, zone/*, dnssec/*, folder/*, hosting/*, shop/*.
MCP Tools группируют их (см. раздел 6). Для сигнатур параметров опирайся на https://www.reg.ru/reseller/api2doc и на карту tools в разделе 6.

## 6. Архитектура MCP-сервера для ИИ-агентов

### 6.1. Архитектурный стек и структура проекта
Рекомендуется реализация на **TypeScript / Node.js** (с использованием официального `@modelcontextprotocol/sdk` и `zod`) либо на **Python** (с использованием `mcp` и `pydantic`).

```text
regru-mcp-server/
├── src/
│   ├── index.ts                 # Точка входа MCP-сервера (stdio / sse транспорт)
│   ├── client/                  # HTTP-клиент к REG.API 2.0
│   │   ├── RegruApiClient.ts    # Транспорт, retry, rate-limiter, обработка ошибок
│   │   ├── auth.ts              # Поддержка парольной и RSA-SHA512 аутентификации
│   │   └── types.ts             # TypeScript интерфейсы для всех ответов и ошибок
│   ├── tools/                   # Группы MCP Tools
│   │   ├── domains.ts           # Tools: check, suggest, info, prices, transfer, contacts
│   │   ├── dns.ts               # Tools: list_records, set_record, delete_record, batch_update
│   │   ├── services.ts          # Tools: list_services, service_details, renew, autorenew
│   │   ├── billing.ts           # Tools: get_balance, list_unpaid_bills, change_payment
│   │   ├── dnssec.ts            # Tools: status, enable, disable, get_records
│   │   └── folders.ts           # Tools: list_folders, move_services
│   ├── resources/               # MCP Resources (состояние аккаунта, DNS-зоны, прайс-лист)
│   └── prompts/                 # MCP Prompts (готовые сценарии для ИИ-ассистентов)
├── package.json
└── tsconfig.json
```

### 6.2. Карта MCP Tools (Инструменты для LLM)
Для оптимального расхода контекста LLM 116 низкоуровневых методов API группируются в эргономичные высокоуровневые инструменты MCP с исчерпывающей JSON-Schema валидацией:

| Имя MCP Tool | Базовые методы API | Описание назначения для ИИ-агента | Обязательные аргументы |
|---|---|---|---|
| `regru_check_domains` | `domain/check`, `domain/get_prices` | Проверка доступности одного или списка доменов для регистрации и получение цен | `domains: string[]`, `currency?: string` |

### 6.3. Карта MCP Resources (Контекстные ресурсы)
MCP Resources позволяют ИИ-агенту считывать контекст инфраструктуры напрямую через URI:
- `regru://account/balance` — Текущий баланс и финансовый статус аккаунта Рег.ру.
- `regru://services/active` — Список всех активных сервисов с датами экспирации.
- `regru://domains/{domain}/dns` — Полное состояние ресурсных записей зоны для указанного домена.
- `regru://pricing/tlds` — Тарифная сетка стоимости регистрации и продления по всем зонам.

### 6.4. Шаблоны MCP Prompts (Сценарии действий для LLM)
1. `audit_expiring_services`: Автоматический аудит услуг, срок действия которых заканчивается в ближайшие 30 дней, проверка баланса и расчет необходимой суммы пополнения.
2. `configure_domain_for_vps`: Полный сценарий привязки купленного домена к новому серверу: установка A-записей `@` и `www`, настройка почтовых MX/SPF/DKIM TXT-записей.
3. `domain_migration_check`: Диагностика домена перед переносом: статус делегирования, проверка authinfo, наличие защиты домена (`DOMAIN_PROTECTION`), верификация ЕСИА.

### 6.5. Паттерны отказоустойчивости, очередей и кэширования
1. **Встроенный Token Bucket Rate Limiter:** Не допускать более 15-18 запросов в минуту от MCP-сервера, чтобы гарантированно не исчерпать часовой лимит 1200 запросов.
2. **Очередь для мутирующих запросов:** Исключить конкурентные вызовы `domain/create`, `service/renew`, `bill/*` во избежание `BILLING_LOCK`.
3. **Безопасная обработка `ok_if_no_money`:** Инструменты заказа и продления должны по умолчанию выставлять `ok_if_no_money=0`, чтобы случайно не создавать неоплаченные финансовые обязательства без явного подтверждения пользователя.
4. **Punycode трансляция:** Входные имена доменов должны автоматически нормализоваться (`foo.рф` -> `xn--foo-qfa.рф`) перед отправкой в транспортный слой API.
